## 🔍 real_reward 的计算过程  # 修改

### 第1步：Gurobi 优化器目标函数（optim.py:44-55）  # 修改

**Gurobi 最大化的目标：**  # 修改

```python  # 修改
Maximize:  # 修改
  Σ car_assignment[i][j] * (car_mem[i][2] - SOC_penalty)  # 修改
  + Σ zone_assignment[i][j]  # 修改
```  # 修改

**组成部分：**  # 修改

1. **订单收益**：`car_mem[i][2]`  # 修改
   - 这是每个订单的价值  # 修改
   - 由参数 `re` 控制（正值 = 订单收益，负值 = 调度成本）  # 修改

2. **SOC 惩罚**：`(SOC_THRESHOLD - car[i][1]) * PENALTY_FACTOR`  # 修改
   - `SOC_THRESHOLD = 600`：电量阈值  # 修改
   - `PENALTY_FACTOR = 50`：惩罚力度  # 修改
   - **只有当 `car[i][1] < 600` 时才惩罚**  # 修改
   - 例如：电量 = 400，惩罚 = (600-400)*50 = 10000  # 修改

3. **区域调度奖励**：`zone_assignment[i][j]`  # 修改
   - 鼓励跨区域调度  # 修改

### 第2步：real_reward 累积（optim.py:119, 153）  # 修改

**在 solveproblem 函数中：**  # 修改

```python  # 修改

# 累积到总 real_reward  # 修改

**关键变量：**  # 修改
- `re`：收益/成本系数  # 修改

- `car[i][2]`：距离（`dist[car[i][0]][j]`）  # 修改

**计算逻辑：**  # 修改
- 完成订单：`real_reward += 正值 * 距离`（收益）  # 修改
- 空驶调度：`real_reward += 负值 * 距离`（成本）  # 修改

## 💡 关键发现  # 修改

### 发现1：real_reward 一直为负  # 修改

**原因：**  # 修改
- 调度成本（空驶）> 订单收益  # 修改
- 或者订单收益系数 `re` 设置较小  # 修改

**影响：**  # 修改
- 这是环境设计的结果，不是 bug  # 修改
- 说明这是一个"成本最小化"问题，而不是"收益最大化"  # 修改

---

### 发现2：固定惩罚 -500 的影响  # 修改

**数值对比：**  # 修改
```  # 修改
每个 step 的 real_reward ≈ -2000  # 修改
固定惩罚 -500 占比 ≈ 25%  # 修改
```  # 修改

**影响：**  # 修改
- 固定惩罚占总 reward 的 1/4  # 修改
- 显著影响最终 reward 的数值  # 修改
- 但不影响优化方向（因为是常数）  # 修改

---

### 发现3：SOC 惩罚的间接作用  # 修改

**机制：**  # 修改
- SOC 惩罚在 Gurobi 目标函数中  # 修改
- 不直接出现在 real_reward 中  # 修改
- 通过影响车辆分配间接影响 real_reward  # 修改

**效果：**  # 修改
- 低电量车辆不被分配订单  # 修改
- 减少因电量不足导致的失败  # 修改
- 鼓励充电行为  # 修改
