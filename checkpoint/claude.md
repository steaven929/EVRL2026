### 1. 训练指标理解 (Training Metrics Understanding)

#### 1.1 Actor Loss 与 Q Value 的关系

**重要发现（2026-01-30）：**

本项目的 Reward 一直为负数（如 -200 逐渐改进到 -50），这导致训练曲线的特殊模式：

##### 训练阶段划分

| 阶段 | 轮数 | Q Value | Actor Loss (-Q) | 含义 |
|------|------|---------|-----------------|------|
| **初始化** | 0 | ≈0 | ≈0 | 网络随机初始化 |
| **探索期** | 0-100 | 0 → -600 | 0 → +600 | Critic 学习真实价值（负 reward） |
| **优化期** | 100-300 | -600 → -300 | +600 → +400 | 策略改进，累积负 reward 减少 ✓ |
| **稳定期** | 300+ | 稳定在 -300 | 稳定在 +400 | 收敛到局部最优 |

##### 关键理解

1. **Q Value 的含义**：
   - Q(s,a) 表示从状态 s 执行动作 a 后的累积回报期望
   - 当环境 reward 为负时，Q 值也为负是正常的
   - **Q 值上升（如 -600 → -300）= 策略改进**

2. **Actor Loss 的含义**：
   - Actor Loss = -Q(s, π(s))（优化目标）
   - 这是用于梯度下降的目标函数，不是性能指标
   - **Actor Loss 下降（如 +600 → +400）= 策略改进**

3. **初期上升是正常的**：
   - 探索期 Q 值下降（0 → -600）是 Critic 在学习真实价值
   - 不是策略恶化，而是从过于乐观的估计回归现实
   - 只有在优化期（Q 值上升）才能判断策略是否改进

##### 诊断代码

已在 `core/algorithm.py` 中添加：
```python
return {
    "critic1_loss": float(critic_loss.item()),
    "actor_loss": float(-policy_q_values.mean().item()),  # -Q值，应该下降
    "q_value": float(policy_q_values.mean().item()),      # Q值，应该上升
    "target_q": float(target_value.mean().item()),        # 目标Q值
}
```

##### 图像解读

- **子图2 (Actor Loss)**：优化期应下降，说明策略改进
- **子图3 (Q Value)**：优化期应上升（变得不那么负），说明累积 reward 改善
- **子图4 (Target Q)**：应与 Q Value 趋势一致
- **子图8 (Reward)**：应逐渐上升（变得不那么负）

#### 1.2 判断训练是否正常

**正常训练的标志：**
1. ✅ 探索期后，Q Value 开始上升
2. ✅ Actor Loss 在优化期下降
3. ✅ Reward 逐渐改进（变得不那么负）
4. ✅ Q Value 和 Target Q 趋势一致

**异常训练的标志：**
1. ❌ Q Value 持续下降超过 200 轮
2. ❌ Actor Loss 持续上升超过 200 轮
3. ❌ Reward 没有改进
4. ❌ Q Value 和 Target Q 严重偏离

**如果出现异常，检查：**
- Critic 学习率是否过高
- Target 网络更新速度（tau）是否过大
- Reward scaling 是否合理
- 网络初始化是否正确

### 2. 超参数调优经验 (Hyperparameter Tuning)

#### 2.1 成功案例：解决 Reward 不改进问题 (2026-01-30)

**问题描述：**
- 初始配置：critic_lr=1e-3, batch_size=32, tau=1e-2
- 训练 300 轮后：Q 值上升但 Reward 没有改进
- 根本原因：Critic 估计偏差，Q 值与实际回报脱节

**解决方案：**
```python
# 调整前
critic_lr = 1e-3      # 过高，导致 Critic 过拟合
batch_size = 32       # 过小，梯度估计噪声大
tau = 1e-2            # 可能偏大

# 调整后
critic_lr = 5e-4      # 降低 50%，减少过拟合  # 修改
batch_size = 64       # 增加 100%，提高稳定性  # 修改
tau = 1e-2            # 保持不变（或可进一步降低到 5e-3）
```

**效果对比：**

| 轮数 | 配置 | Q Value 变化 | Reward 变化 | 结论 |
|------|------|-------------|------------|------|
| 300轮 | 旧参数 | 0 → -600 → -300 | 无明显改进 | ❌ Critic 估计偏差 |
| 700轮 | 新参数 | -366.79 → -349.97 | -2683 → -2294 (+14.5%) | ✅ 训练成功 |

**关键指标：**
- Q Value 上升：+16.81
- Reward 改进：+389.35 (约 14.5%)
- Actor Loss 下降：-16.81

**经验总结：**
1. **Critic 学习率是关键**：过高会导致 Q 值估计不准确
2. **Batch Size 影响稳定性**：增大可以减少梯度噪声
3. **Q 值和 Reward 必须一致**：如果 Q 值上升但 Reward 不变，说明 Critic 有问题
4. **耐心调参**：从 300 轮到 700 轮，参数调整后效果显著

### 4. 近似最优解方法（2026-02-01）

**问题背景**：
- 全局最优求解（12步，18车，4区域）计算时间过长（可能数小时）
- 需要快速获得高质量的近似最优解作为RL训练的上界参考

**解决方案**：实现了两种互补的近似方法

#### 4.1 方法1：滚动时域优化（Rolling Horizon）

**原理**：
- 每次只优化未来 `horizon` 步（推荐3-4步）
- 执行第一步决策后，滚动前进到下一时刻
- 重复上述过程直到完成所有时间步

**优点**：
- ✅ 求解速度快：10-30秒（相比全局求解的数小时）
- ✅ 质量高：通常在全局最优的95-98%
- ✅ 实用性强：符合实际在线调度场景

**使用方法**：
```bash
# 运行滚动时域优化（horizon=4）
python optimal_solver.py --method rolling --horizon 4

# 输出文件：rolling_horizon_solution.json
```

**关键参数**：
- `horizon=4`：优化时域长度（推荐3-4步）
- `mip_gap=0.01`：每步的MIPGap（1%）
- `time_limit_per_step=30`：每步时间限制（秒）

**预期性能**：
- Reward差距：2-8%（相比全局最优）
- 求解时间：约20-30秒（12步总计）
- 适用场景：日常对比、快速验证

#### 4.2 方法2：参数优化全局求解

**原理**：
- 仍然求解全局12步问题
- 但设置 `MIPGap` 和 `TimeLimit` 参数
- Gurobi在时间限制内返回当前最优解

**优点**：
- ✅ 提供理论保证：MIPGap=5%表示解在最优解的95%以上
- ✅ 可控时间：设置10分钟时间限制
- ✅ 学术认可度高：可用于论文对比

**使用方法**：

**关键参数**：

### 5. 新奖励函数设计（2026-02-02）

**问题背景**：
- 旧奖励函数：`Reward = sum(real_reward) / 10 - 500`
- 主要问题：
  1. 固定惩罚-500占主导地位（12步总计-6000）
  2. 没有充电激励
  3. 没有低电量惩罚
  4. 调度成本太小（0.0001，几乎可忽略）

**新奖励函数设计**：

```python
新Reward = 服务订单收益 + 充电加分 - 低电量惩罚 - 调度成本 - 固定惩罚
```

#### 5.1 四个组成部分

**1. 服务订单收益**
```python
服务订单收益 = sum(1.5 * dist * 服务订单数)
```
- 保持原有逻辑
- 鼓励服务更多订单，尤其是长距离订单

**2. 充电加分**
```python
充电加分 = 50 * 充电车辆数
```
- 每辆车充电奖励50分
- 鼓励车辆及时充电，避免电量耗尽

**3. 低电量惩罚（分段惩罚）**
```python
对每辆车：
  if SOC >= 600:
      惩罚 = 0
  elif 200 <= SOC < 600:
      惩罚 = 0.5 * (600 - SOC)  # 轻度惩罚
  else:  # SOC < 200
      惩罚 = 0.5 * 400 + 5.0 * (200 - SOC)  # 重度惩罚

总惩罚 = sum(所有车辆的惩罚)
```

**惩罚示例**：
- SOC=800：惩罚=0
- SOC=500：惩罚=50（轻度）
- SOC=200：惩罚=200（临界）
- SOC=100：惩罚=700（重度）
- SOC=0：惩罚=1200（极重）

**4. 调度成本**
```python
调度成本 = sum(0.01 * dist * 调度订单数)
```
- 从0.0001提高到0.01
- 使调度成本更明显，约束无效调度

**5. 固定惩罚**
```python
固定惩罚 = 500（每步）
```
- 保持不变

#### 5.2 完整公式

```python
Reward = (sum(1.5 * dist * 服务订单)
         + 50 * 充电车辆数
         - sum(分段低电量惩罚)
         - sum(0.01 * dist * 调度订单)) / 10
         - 500
```

**重要说明**：添加了缩放因子 `/10` 以控制波动

**原因**：
- 服务订单收益范围：1,800 - 24,000（每步）
- 不加缩放会导致每步波动达23,000+
- 添加 `/10` 后波动范围：180 - 2,400（可控）

#### 5.3 预期效果

**旧奖励函数（理论最优）**：
```
服务所有195个订单：
real_reward = 188,550
Reward = 188,550 / 10 - 500 * 12 = 18,855 - 6,000 = 12,855
```

**新奖励函数（理论最优）**：
```
服务所有195个订单：
服务收益 = 188,550
充电加分 = 50 * 假设5辆车充电 = 250
低电量惩罚 = 假设平均SOC=1000，惩罚=0
调度成本 = 假设调度50次，平均距离400，成本=200

新Reward = (188,550 + 250 - 0 - 200) / 10 - 500 * 12
         = 18,860 - 6,000
         = 12,860
```

**对比**：
- 旧奖励函数理论最优：12,855
- 新奖励函数理论最优：12,860
- **数值范围相近，易于对比**

**波动范围对比（每步）**：
- 旧函数：-320 ~ 1,900（波动2,220）
- 新函数（无缩放）：220 ~ 23,710（波动23,490）❌
- 新函数（有缩放/10）：-320 ~ 2,371（波动2,691）✅
