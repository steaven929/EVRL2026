1. 项目概述
本项目是一个基于深度强化学习（DDPG）与混合整数规划（MIP/Gurobi）结合的电动汽车车队调度与充电管理系统。 主要解决在时变小路网下，考虑固定停车位约束、即时充电逻辑以及低廉固定电费场景下的车辆调度与能量管理问题。

核心特性：

混合决策架构：RL (DDPG) 负责高层决策（区域调度倾向、充电倾向），Gurobi 负责底层具体的车辆-订单匹配与路径规划。

物理约束增强：引入了具体的“充电桩”与“普通车位”概念，严格限制物理占用，防止“幽灵停车”。

SOC 软约束优化：在底层优化器中加入了 SOC（电量）惩罚项，强制调度器避免使用低电量车辆。

2. 代码结构说明
核心入口
main.py: 项目主入口。负责加载配置、初始化环境 (dclily)、加载数据、训练/测试 Agent、以及绘图（Reward/Battery Heatmap）。

Specific (环境与业务逻辑核心)
这是本项目修改幅度最大的部分，位于 /specific/ 目录下。

1. config.json (路网配置)
定义了路网的拓扑结构和物理资源限制。

关键更新：不再使用单一的 NUM_CHARGERS，而是通过 ZONES 列表详细定义每个区域的资源。

JSON

"ZONES": [

  },

2. dclily_elec.py (Gym 环境)
实现了具体的车辆状态流转、充电逻辑和物理占用判定。

状态空间 (Observation Space):

展平的一维向量，包含：[OD需求(In/Out) + 充电桩占用状态 + 充电桩配置数量]。

动作空间 (Action Space):

维度：3 * ZONE_NUM (连续值 0~1)

[0 : ZONE_NUM]: 发车倾向 (Departure Preference)

[ZONE_NUM : 2*ZONE_NUM]: 目的地倾向 (Destination Preference)

[2*ZONE_NUM : 3*ZONE_NUM]: 充电倾向 (Charging Preference) —— (New!) RL 显式输出是否希望车辆去充电。

核心逻辑 (step):

车辆移动与到达：更新车辆位置与剩余里程。

物理占用同步：到达车辆会根据 charger_id 锁定 charging_stations 中的物理资源，实现“人车桩合一”。

空闲车辆充电决策 (check_idle_vehicles):

结合 RL 输出的 charge_pref、车辆当前 SOC、距离最近充电站距离，计算充电概率。

若决定充电，自动规划前往有桩区域，并预占充电位。

调度与匹配: 调用 optim.solveproblem。

能量更新: 简单的线性/非线性充电函数模拟电池回充。

3. optim.py (Gurobi 优化器)
负责在 RL 给出的宏观指令下，进行微观的订单匹配。

目标函数更新:

Maximize: (订单收益) - (调度成本) - (SOC惩罚)

SOC 惩罚机制 (New!):

Python

# 当电量低于 SOC_THRESHOLD (如600) 时，施加巨大的 PENALTY_FACTOR
penalty = (SOC_THRESHOLD - car[i][1]) * PENALTY_FACTOR
这确保了优化器不会指派低电量车辆去执行长距离任务，间接实现了“低电量保护”。

3. 关键逻辑详解 (Attention for AI Analysis)
如果你（AI 助手）需要分析代码逻辑，请特别关注以下流程：

A. 充电决策流程
RL 触发: 在 dclily_elec.py 的 check_idle_vehicles 中，根据 step 传入的 Action 后 1/3 部分（充电倾向）计算概率。

位置寻找: find_preferred_charger 或 find_nearest_charger 寻找有空闲桩的区域。

预占位: 调用 assign_parking_slot(..., is_charging_order=True)。

如果目标区域没桩了，车辆会被标记为 charger_id = -1（排队或普通停车）。

如果有桩，charger_id 被赋值，且在该车到达前，该桩逻辑上被“预订”。

B. 幽灵停车 (Ghost Parking) 防护
在 assign_parking_slot 中包含了一套兜底逻辑：如果区域内普通车位已满但充电桩有空，普通车辆（非充电任务）会被迫占用充电桩（occupied_by 置位），这模拟了燃油车占位或资源挤兑的现实情况。

C. Gurobi 交互
环境 (dclily) 将车辆列表 self.car 和资源表 self.available 传给 optim.solveproblem。

重要: 只有 charger_id == -1 (未在充电/未锁定桩) 的车辆，才会将其计入 available 传给 Gurobi 进行调度。正在充电的车对调度器是不可见的。

7.3 reward_analysis.md (奖励函数组成分析)
深入分析当前奖励函数的计算过程和各组成部分的作用。

主要内容：
- real_reward 的计算过程：Gurobi 优化器 → 累积收益/成本 → 最终 reward
- 组成部分详解：
  * 订单收益（re * distance，re > 0）
  * 调度成本（re * distance，re < 0）
  * SOC 惩罚（间接影响，在 Gurobi 目标函数中）
  * 缩放因子（/10）
  * 固定惩罚（-500）

关键发现：
- 这是成本最小化问题（real_reward 为负）
- 固定惩罚 -500 占总 reward 的 25%
- 700轮训练：real_reward 改进约 18%（-21830 → -17940）

7.4 debugging_plan.md (调试计划)

- 实验步骤：短期诊断 → 参数调优 → 长期训练
