================================================================================
实验4：增强SOC维持奖励机制
================================================================================
实验时间: 2026.2.11
基于实验: 实验3（充电奖励1500）
修改目标: 让Actor从状态中直接感知低SOC的危险性，而不仅依赖充电动作奖励

================================================================================
问题分析
================================================================================

实验3结果：
- 充电奖励从500提升到1500（3倍），但Actor仍不学习充电
- Actor输出充电偏好：10^-9到10^-5级别（远低于0.1阈值）
- RL测试期只充电2次 vs 最优解128次
- RL总奖励9820 vs 最优解24054.83（仅40.8%）

根本原因：
1. 充电的长期价值没有被正确传递给Actor
2. Critic可能低估了充电的价值（gamma=0.95导致信用分配困难）
3. 现有SOC惩罚力度不够，Actor感知不到低SOC的危险

解决思路：
- 不再仅仅奖励"充电动作"
- 而是直接惩罚"低SOC状态"
- 让Actor从状态中立即感知到低电量的危险
- 避免时间折扣导致的信用分配问题

================================================================================
修改内容
================================================================================

文件1：specific/dclily_elec.py（RL环境）

修改1：增强SOC分段惩罚（line 1228-1248）

原逻辑：
  if soc >= 600:
      penalty = 0
  elif soc >= 200:
      penalty = 0.5 * (600 - soc)
  else:
      penalty = 0.5 * 400 + 5.0 * (200 - soc)

新逻辑：
  if soc >= 600:
      penalty = 0
  elif soc >= 400:  # 扩大惩罚范围：从200提升到400
      penalty = 2.0 * (600 - soc)  # 增强惩罚力度：从0.5提升到2.0
  elif soc >= 200:
      penalty = 2.0 * 200 + 10.0 * (400 - soc)  # 从5.0提升到10.0
      low_soc_count += 1
  else:
      penalty = 2.0 * 200 + 10.0 * 200 + 50.0 * (200 - soc)  # 极低电量巨大惩罚
      low_soc_count += 1

修改2：添加低电量车辆数惩罚（line 1248）

新增逻辑：
  low_soc_vehicle_penalty = low_soc_count * 500
  soc_penalty += low_soc_vehicle_penalty

影响：
  - 每辆低电量车辆（SOC < 400）额外惩罚500
  - 让Actor直接感知到"低电量车辆数"这个状态特征
  - 避免时间折扣问题，即时反馈

修改3：终止时同步更新（line 1280-1298）
  - 保持一致性，终止时也使用相同的增强SOC惩罚

文件2：optimal_solver.py（最优解求解器）

修改4：同步增强SOC惩罚（line 153-192）

新增约束：
  1. 分段惩罚线性化：
     - penalty >= 2.0 * (600 - soc)
     - penalty >= 3200 - 8.0 * soc  (当soc < 400)
     - penalty >= 11600 - 50.0 * soc  (当soc < 200)

  2. 低电量指示器（二值变量）：
     - low_soc_indicator[v,t] = 1 当 soc < 400
     - 使用大M方法实现

  3. 低电量车辆数惩罚：
     - low_soc_vehicle_penalty = 500 * sum(low_soc_indicator)

影响：
  - 最优解与RL使用完全相同的奖励函数
  - 确保公平对比

================================================================================
惩罚力度对比
================================================================================

SOC区间 | 原惩罚系数 | 新惩罚系数 | 提升倍数
--------|-----------|-----------|----------
600+    | 0         | 0         | -
400-600 | 0.5       | 2.0       | 4倍
200-400 | 0.5       | 10.0      | 20倍
<200    | 5.0       | 50.0      | 10倍

额外惩罚：
- 原：无
- 新：每辆低电量车辆（SOC<400）额外惩罚500

示例计算（假设18辆车）：

场景1：所有车辆SOC=500
- 原惩罚：18 * 0.5 * 100 = 900
- 新惩罚：18 * 2.0 * 100 = 3600
- 提升：4倍

场景2：所有车辆SOC=300
- 原惩罚：18 * 0.5 * 300 = 2700
- 新惩罚：18 * (2.0*200 + 10.0*100) + 18*500 = 18*(400+1000) + 9000 = 34200
- 提升：12.7倍

场景3：所有车辆SOC=100
- 原惩罚：18 * (0.5*400 + 5.0*100) = 18 * 700 = 12600
- 新惩罚：18 * (2.0*200 + 10.0*200 + 50.0*100) + 18*500 = 18*7400 + 9000 = 142200
- 提升：11.3倍

================================================================================
风险评估
================================================================================

潜在风险：
1. 过度充电：Actor可能为了避免惩罚而过度充电
   - 缓解：充电也有成本（占用充电桩），会自然平衡

2. 训练不稳定：惩罚力度过大可能导致梯度爆炸
   - 缓解：奖励已经除以10进行缩放

3. 最优解求解变慢：增加了二值变量
   - 缓解：只有18*13=234个二值变量，Gurobi应该能快速求解
